{{- if and .Values.registry.enabled (not .Values.registry.host) }}

WARNING: registry.host is not set, so published references name the in-cluster Service.

The controllers can push and refresh over cluster DNS, but a POD CANNOT PULL from that name:
containerd resolves image references with the node's resolver, which does not see cluster DNS.
Images will publish successfully and then fail to pull with ErrImagePull.

Set registry.host to a name that resolves BOTH on your nodes and inside the cluster, and point it
at this registry. Both matter: the nodes pull with it, and the controllers push and refresh with
it, and status.artifact.ref carries only one string. A name only the nodes know fails the other
way -- every object reports "no such host" and publishes nothing.

An ingress does both. Otherwise registry.service.type=NodePort plus a containerd drop-in on each
node, and a CoreDNS hosts entry for the cluster side:

    /etc/containerd/certs.d/<registry.host>/hosts.toml
    [host."http://<node>:<nodePort>"]
      capabilities = ["pull", "resolve"]

If that registry.host speaks plain HTTP -- a NodePort does -- also set defaultRegistry.insecure to
it. It is not assumed: registry.host is just as often an ingress terminating TLS, and marking that
insecure would force plaintext on the deployment that took the trouble to set it up.

See docs/registry.md.
{{- end }}

{{- if gt (int .Values.registry.readReplicas) 0 }}

The registry has {{ .Values.registry.readReplicas }} READ REPLICA(S) alongside one writer.

Pulls fan out across all of them, so a node drain no longer takes image pulls down with it. Pushes
still go to the single writer: while that pod is moving, publishing pauses and the controllers retry
on the next reconcile. Nothing is lost, but it is not instant.

Replicas may only read. zot serialises repository writes with an in-process lock, so a second
writer -- including one that merely garbage-collects -- silently loses content. See
docs/adr/0041-one-writer-many-readers.md.

The replicas are spread across nodes on a PREFERRED rule, so if the scheduler could not place them
apart they may share a node, and then a node failure still takes them all. Check with:

  kubectl -n {{ .Release.Namespace }} get pods -l oci-composer.lhns.de/registry-role=serve -o wide

{{- if eq .Values.registry.storage.driver "local" }}

The replicas share one volume. The chart checked that you ASKED for ReadWriteMany; it cannot check
that your StorageClass delivers it. A provisioner that binds the claim and backs it per-node instead
gives you pods serving different content behind one Service name. Confirm before relying on it:

  kubectl -n {{ .Release.Namespace }} get pvc {{ include "kube-oci-composer.registryFullname" . }}
{{- end }}
{{- if eq .Values.registry.cache.driver "redis" }}

If that redis is not persistent, READ THIS. extensions.search records the pull timestamps the
retention policy depends on, and with replicas that metadata lives in redis rather than on each pod.
A redis restart loses every timestamp, every image then looks unpulled, and the next GC pass
reclaims images your live objects still reference -- on a gcDelay fuse, not a retention window.
{{- end }}
{{- end }}

REFERENCE A DIGEST, NEVER THE TAG. The tag moves; a workload pinned to it plus
pullPolicy: IfNotPresent will silently keep stale bytes. See docs/adr/0010.

Check on it with:

    kubectl get imagecomposition -A
{{- if .Values.imageBuild.enabled }}
    kubectl get imagebuild -A
{{- end }}

{{- if and .Values.registry.enabled (not .Values.registry.persistence.enabled) }}

WARNING: registry.persistence is off, so the registry stores images in an emptyDir.

Every restart loses every image. For ImageComposition that is recoverable -- artifacts rebuild from
their specs -- but an ImageBuild's output cannot be reproduced (ADR 0025), so those are gone.
{{- end }}

{{- if and .Values.imageComposition.enabled (not .Values.operator.s3.endpoint) }}

The layer cache is local to this pod, so a restart or a reschedule re-fetches every layer from
upstream. Set operator.s3.endpoint to keep it across both.
{{- end }}

{{- if eq (int .Values.operator.keepBuilds) 0 }}

operator.keepBuilds is 0, which will be clamped to 1. Only the newest build stays pullable, so reverting
a commit or rescheduling a pod pinned to an older digest will fail.
