# 33. One chart, one namespace, toggleable components

Date: 2026-08-20

## Status

Accepted. Reverses the packaging half of [0004](0004-two-kinds-two-controllers.md) and the
opt-in-install argument in [0025](0025-dockerfile-builds-as-a-second-kind.md):206-210.

The *runtime* separation 0004 argues for is kept in full. What changes is how it is delivered.

## Context

Two charts in two namespaces made one thing genuinely hard and one thing genuinely confusing.

**The hard thing: shared credentials.** [0030](0030-a-real-registry-serves-both-kinds.md) made a
registry the serving surface for both kinds, and
[0031](0031-the-retention-guarantee.md) made both controllers talk to it continuously. Both need the
same push credential. A controller reads a Secret from its own namespace, so two namespaces means
two Secrets holding the same password, generated by one chart and somehow delivered to the other.
Every option was bad: cross-namespace writes from a chart that does not own the namespace, a `lookup`
that returns nothing during `helm template`, or an operator copying a generated password between two
installs and calling it automatic.

One namespace makes the problem disappear rather than solving it.

**The confusing thing: two charts for one system.** Installing the composer left `ImageBuild`
objects unreconciled with no signal beyond the absence of a controller, and the relationship between
the two releases was documentation rather than structure.

### What 0004 and 0025 actually argued

Worth separating, because only part of it is being reversed.

0004 separates *components*: separate binaries, separate ServiceAccounts, separate RBAC. That
argument is untouched and the separation is preserved exactly.

0025:206-210 goes further and makes installation itself the boundary: "Installing the composer does
NOT install this. Its role can create Jobs — that is, run arbitrary containers — which is exactly
why it is a separate thing you opt into." **That** is what this record reverses, and it is a real
reduction in safety-by-default.

## Decision

**One chart, `kube-oci-composer`, deploying up to three components into one namespace**, each
toggleable and all on by default:

| Toggle | Deploys |
|---|---|
| `imageComposition.enabled` | the composer controller, its Service, its storage |
| `imageBuild.enabled` | the builder controller **and its RBAC** |
| `registry.enabled` | the bundled zot, its credentials, its storage |

`charts/kube-oci-builder` is deleted.

**The runtime separation is unchanged.** Two Deployments, two ServiceAccounts, two ClusterRoles. The
composer's role still cannot create a single object; the builder's still can create Jobs. Merging the
charts did not merge the permissions, and a parity test asserts each role still matches its generated
kubebuilder markers.

**`imageBuild.enabled=false` removes the RBAC, not just the controller.** A toggle that left the
Role behind would be a setting that looks like a security control and is not one. Asserted: with the
toggle off, no rendered role grants `jobs`.

**CRDs move from `crds/` to `templates/`.** Helm installs `crds/` once and never upgrades it, which
is why the `DockerBuild` → `ImageBuild` rename needed CRD surgery by hand. Both CRDs carry
`helm.sh/resource-policy: keep`, emitted by a kubebuilder marker on the Go type so the chart can
install the generated file verbatim. They install regardless of the toggles: **deleting a CRD deletes
every object of that kind**, and an unused API costs nothing next to that.

## Consequences

**A default install can run arbitrary containers, and that is a real loss.** This is the cost 0025
priced and refused to pay, now paid. Three things make it defensible rather than merely convenient:
the capability is one value away from gone, turning it off removes the permissions rather than
hiding them, and the alternative — two charts — demonstrably failed to deliver a working system
without manual credential plumbing.

An operator who wants 0025's posture back sets `imageBuild.enabled=false`, and gets exactly what
installing only the composer chart used to give.

**Everything lands in one namespace.** Blast radius within it is unchanged, because RBAC is unchanged
— but the builder's ServiceAccount and the composer's are now neighbours, and a NetworkPolicy or a
quota that used to separate them by namespace no longer does.

**Upgrading from two releases is not automatic.** `helm uninstall kube-oci-builder` and reinstall the
composer chart with `imageBuild.enabled=true`. The CRD survives (`resource-policy: keep`), so
`ImageBuild` objects survive with it.

**The chart is now a component of the system rather than a wrapper around a binary**, which is why
its templates carry component labels. Before this, every pod in the release answered every Service's
selector; the registry pod was already backing the composer's Service, and the composer's own pod
template was missing the label its Service selected on. Both were found by a test written for this
change, not in a cluster.
